# 資料庫設計（Database Design）

## 1 資料庫設計概述

BookHub 使用 **Neon PostgreSQL** 作為資料庫管理系統，採用關聯式資料庫（Relational Database）的設計方式，將不同類型的資料儲存在獨立的資料表（Table）中。

本系統的主要資料包含會員資訊、書籍商品、購物車、訂單、訂單明細及賣家評價。

為了避免資料重複、方便後續維護，以及確保資料之間的關聯性，我們將系統分成六張主要資料表：

| Table | 中文名稱 | 主要功能 |
|---|---|---|
| `users` | 使用者資料表 | 儲存買家與賣家的基本資訊 |
| `books` | 書籍資料表 | 儲存賣家上架的二手書資訊 |
| `cart_items` | 購物車資料表 | 記錄買家加入購物車的商品 |
| `checkout_orders` | 訂單資料表 | 記錄每次結帳的訂單 |
| `checkout_order_items` | 訂單明細資料表 | 記錄每張訂單所購買的書籍 |
| `seller_reviews` | 賣家評價資料表 | 儲存買家對賣家的評分與評論 |

透過這六張資料表，我們可以將不同的系統功能連接起來，形成完整的二手書交易流程。

## 2 Primary Key 與 Foreign Key

在關聯式資料庫中，我們主要使用兩種重要的 Key 來建立資料之間的關係。

### Primary Key（主鍵，PK）

Primary Key 是用來唯一識別資料表中每一筆資料的欄位。

例如，在 `users` 資料表中：

| id (PK) | name | role |
|---|---|---|
| 1 | Amy | BUYER |
| 2 | John | SELLER |
| 3 | Peter | BUYER |

每位使用者都有不同的 `id`，即使兩位使用者姓名相同，也可以透過 `id` 區分不同帳號。

因此，Primary Key 必須具有唯一性，且不可為 NULL。

### Foreign Key（外鍵，FK）

Foreign Key 用來建立不同資料表之間的關聯。

例如，在 `books` 資料表中：

| id (PK) | title | seller_id (FK) |
|---|---|---|
| 101 | Calculus | 2 |
| 102 | Linear Algebra | 2 |
| 103 | Database Systems | 2 |

這裡的 `seller_id` 對應 `users.id`。

也就是說，這三本書都是由 `id = 2` 的使用者 John 上架。

透過 Foreign Key，系統不需要在每一筆書籍資料中重複儲存賣家姓名及電子郵件，而是可以利用 `seller_id` 查詢對應的賣家資訊。

這樣可以減少資料重複，並維持資料的一致性。

## 3 資料表詳細介紹

### Table 1：Users（使用者資料表）

`users` 用來儲存所有註冊使用者的資訊。

| 欄位 | 說明 |
|---|---|
| `id` | 使用者唯一編號（PK） |
| `name` | 使用者姓名 |
| `email` | 電子郵件，不可重複 |
| `password_hash` | 經過雜湊處理的密碼 |
| `role` | 使用者身分（BUYER / SELLER） |
| `created_at` | 帳號建立時間 |
| `seller_bio` | 賣家個人介紹 |

BookHub 沒有為買家和賣家分別建立獨立的會員資料表，而是透過 `role` 欄位區分使用者角色。

這樣可以簡化會員管理，也避免重複設計登入、註冊及密碼驗證功能。

### Table 2：Books（書籍資料表）

`books` 用來儲存平台中所有上架的書籍資訊。

| 欄位 | 說明 |
|---|---|
| `id` | 書籍唯一編號（PK） |
| `seller_id` | 上架書籍的賣家編號（FK） |
| `title` | 書籍名稱 |
| `price` | 販售價格 |
| `condition` | 書籍狀況 |
| `status` | 商品狀態 |
| `image_url` | 書籍圖片位置 |
| `college` | 學院分類 |
| `created_at` | 商品上架時間 |

其中，`seller_id` 連接到 `users` 資料表，讓系統可以知道每本書是由哪位賣家上架。

`condition` 用來記錄書況，例如 NEW、LIKE_NEW、GOOD 和 FAIR。

`status` 則用來區分 AVAILABLE、RESERVED 和 SOLD 等商品狀態。

另外，我們使用 `college` 欄位進行學院分類，讓買家可以依照理學院、文學院或管理學院等分類搜尋書籍。

### Table 3：Cart Items（購物車資料表）

`cart_items` 用來記錄買家加入購物車的商品。

| 欄位 | 說明 |
|---|---|
| `id` | 購物車項目編號（PK） |
| `buyer_id` | 買家編號（FK） |
| `book_id` | 書籍編號（FK） |
| `created_at` | 加入購物車時間 |

當買家點選「加入購物車」時，系統會在資料庫中建立一筆紀錄。

例如：

| id | buyer_id | book_id |
|---|---|-----|
| 1 | 1 | 101 |
| 2 | 1 | 102 |
| 3 | 3 | 101 |

這個例子代表買家 1 的購物車有兩本書，而買家 3 也將書籍 101 加入購物車。

同一本書可以同時出現在不同買家的購物車中，但在真正結帳時，系統仍然需要確認商品是否可以購買。

### Table 4：Checkout Orders（訂單資料表）

`checkout_orders` 用來記錄買家完成結帳後建立的訂單。

| 欄位 | 說明 |
|---|---|
| `id` | 訂單編號（PK） |
| `buyer_id` | 下單買家編號（FK） |
| `total_amount` | 訂單總金額 |
| `created_at` | 訂單建立時間 |

例如：

| id | buyer_id | total_amount |
|---|---|---|
| 1001 | 1 | 650 |
| 1002 | 3 | 350 |

第一筆訂單代表買家 1 建立了一筆總金額為 650 元的訂單。

但這張表不會直接列出每一本購買的書籍，因此需要另一張資料表來記錄訂單內容。

### Table 5：Checkout Order Items（訂單明細資料表）

`checkout_order_items` 用來記錄每一筆訂單中包含的書籍。

| 欄位 | 說明 |
|---|---|
| `id` | 訂單明細編號（PK） |
| `order_id` | 所屬訂單編號（FK） |
| `book_id` | 購買的書籍編號（FK） |
| `title` | 購買當下的書名 |
| `price` | 購買當下的價格 |
| `image_url` | 購買當下的書籍圖片位置 |

例如：

| id | order_id | book_id | price |
|---|---|---|---|
| 1 | 1001 | 101 | 350 |
| 2 | 1001 | 102 | 300 |
| 3 | 1002 | 103 | 350 |

可以看到，訂單 1001 包含兩本書，總金額為 650 元。

我們將訂單與訂單明細分開設計，是為了讓一張訂單可以包含多本書籍，而不需要在同一個欄位中儲存多個商品編號。

另外，系統會保留購買當下的書籍名稱與價格，避免商品資訊日後修改時影響歷史訂單。

### Table 6：Seller Reviews（賣家評價資料表）

`seller_reviews` 用來記錄買家完成購買後，對賣家留下的評分與評論。

| 欄位 | 說明 |
|---|---|
| `id` | 評價編號（PK） |
| `order_item_id` | 對應的訂單明細（FK、UNIQUE） |
| `buyer_id` | 撰寫評價的買家（FK） |
| `seller_id` | 被評價的賣家（FK） |
| `rating` | 一至五顆星 |
| `comment` | 文字評論 |
| `created_at` | 評價建立時間 |

為了避免重複評價，系統以 `order_item_id` 作為唯一限制欄位。

也就是說，同一筆購買明細最多只能建立一筆賣家評價。

買家可以透過評價功能分享交易經驗，而其他使用者也能在賣家個人檔案中查看相關評論。

## 4 資料表之間的關係（Relationships）

BookHub 主要使用三種關聯式資料庫概念：一對一、一對多，以及多對多。

### （一）一對一（One-to-One, 1:1）

一對一代表一筆資料最多對應另一張資料表中的一筆資料。

在 BookHub 中，`checkout_order_items` 與 `seller_reviews` 採用一對零或一的關係（1:0..1）。

原因是：

- 每一筆訂單明細可以尚未被評價。
- 完成評價後，該訂單明細最多只會對應一筆賣家評價。
- `seller_reviews.order_item_id` 使用 UNIQUE 限制，避免重複評論。

例如：

訂單明細 #101 → 賣家評價 #1

訂單明細 #102 → 尚未評價

因此，這不是強制每筆訂單明細都要有評價，而是可選擇的一對一關係。

### （二）一對多（One-to-Many, 1:N）

一對多代表一筆資料可以對應另一張資料表中的多筆資料。

這是 BookHub 最常使用的關係。

**範例 1：Users → Books**

一位賣家可以上架多本書，但每本書只屬於一位賣家。

例如：

John（Seller ID = 2）

→ Calculus

→ Linear Algebra

→ Database Systems

這代表 Users 與 Books 是一對多的關係。

**範例 2：Users → Checkout Orders**

一位買家可以建立多筆訂單，但每筆訂單只屬於一位買家。

**範例 3：Checkout Orders → Checkout Order Items**

一筆訂單可以包含多本書，而每筆訂單明細只屬於一張訂單。

### （三）多對多（Many-to-Many, M:N）

多對多代表一筆資料可以對應另一張資料表中的多筆資料，而反過來也成立。

例如：

- 一位買家可以將多本書加入購物車。
- 同一本書也可能被多位買家加入各自的購物車。

因此，買家與書籍在購物車功能中形成多對多的關係。

在關聯式資料庫中，我們可以透過中介資料表（Junction Table）來處理多對多關係。

BookHub 使用 `cart_items` 作為中介資料表。

也就是：

Users（1:N）→ Cart Items ←（N:1）Books

如此一來，就能透過 `buyer_id` 與 `book_id` 記錄買家和書籍之間的關係。

需要注意的是，購物車允許同一本商品被多位買家加入，但完成結帳後，系統會更新書籍狀態，避免同一本二手書被重複出售。

## 5 為什麼要將訂單拆成兩張 Table？

如果將訂單與商品全部放在同一張資料表中，可能產生資料重複的問題。

例如，同一張訂單包含三本書，如果只有一張大表，就必須重複儲存相同的買家資訊、訂單日期與訂單總額。

因此，我們將訂單資料拆成：

**Checkout Orders**

負責儲存訂單的主要資訊，例如買家、總金額及建立時間。

**Checkout Order Items**

負責儲存訂單中每一本書籍的詳細資料。

兩張表透過 `order_id` 建立一對多關係。

這種方式可以減少重複資料，也讓未來增加商品數量或查詢歷史訂單更加容易。

## 6 資料完整性與交易安全

為了確保資料的正確性，BookHub 使用以下設計方式：

**1. 主鍵與外鍵**

透過 Primary Key 唯一識別每筆資料，並利用 Foreign Key 建立資料表之間的關係。

**2. 唯一性限制**

例如，會員的電子郵件不可重複，同一筆訂單明細也不能重複建立賣家評價。

**3. 資料驗證**

系統會檢查書籍價格、書況、學院分類，以及賣家評分是否符合規定。

**4. 資料庫交易（Transaction）**

結帳時，系統會在同一筆資料庫交易中處理訂單建立、訂單明細寫入、商品狀態更新及購物車清除。

**5. 資料列鎖定（Row-Level Locking）**

由於二手書通常只有一本，結帳時會鎖定相關書籍資料列，避免不同買家同時購買同一本商品。

透過這些設計，可以提高交易資料的一致性，降低重複購買及資料異常的風險。

## 7 資料庫設計總結

BookHub 的資料庫設計以關聯式資料庫為核心，透過六張主要資料表管理會員、書籍、購物車、訂單及評價資料。

本系統運用一對多、一對一及多對多的關係，讓不同資料表能夠互相連接，同時保留各自的功能與資料結構。

其中，`cart_items` 負責處理買家與書籍之間的多對多關係；`checkout_orders` 與 `checkout_order_items` 則透過一對多關係管理訂單內容；`seller_reviews` 透過唯一限制，避免同一筆購買明細重複評價。

藉由主鍵、外鍵、資料驗證及交易機制，我們希望建立一個結構清楚、容易維護，並能支援完整買賣流程的校園二手書交易系統。
